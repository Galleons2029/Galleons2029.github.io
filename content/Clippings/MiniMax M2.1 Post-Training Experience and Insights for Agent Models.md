## MiniMax M2.1：代理模型的训练后经验和见解

## 模型概述

M2.1 是上个月发布的最新旗舰级开源模型，它在前代 M2 模型的基础上进行了进一步的后训练优化。该模型采用 **混合专家（MoE）架构，** **总参数量** 约为2300 亿 ， **激活参数量约为 100 亿。**  
在智能体场景中，M2.1 展现出卓越的可用性。即使激活参数量相对较少，它也能保持较高的推理效率和强大的性能，为各种实际应用提供了稳定且可用于生产环境的工程能力。

## 智能体数据合成

我们首先进行数据综合，数据综合大致可以分为三类：  
- **基于真实数据的综合：SWE 扩展**
- **专家主导的综合：应用开发**
- **虚拟长时任务合成：WebExplorer**
前两个主要针对编码场景，而最后一个则侧重于更通用的搜索任务。

![](https://www.minimax.io/_next/image?url=https%3A%2F%2Ffile.cdn.minimax.io%2Fpublic%2Fb3a9491f-c3b6-42e8-b659-6a7d2dd8158a.png&w=3840&q=75)

### 基于真实数据的综合：SWE 扩展

SWE Scaling 的核心在于针对软件工程场景的数据扩展。我们利用 GitHub 这个庞大且结构良好的数据源，生成各种可验证的任务。借助这些任务，我们可以在坚实的数据基础上，高效地执行拒绝采样、构建 SFT 数据集或进行强化学习 (RL)。

**数据管道概述**

原始数据源包括 GitHub 的拉取请求 (PR) 和提交记录 (Commit)。我们首先进行质量过滤——简单的规则包括选择最终被合并的 PR，以及其他标准，例如是否存在相关的测试用例。  
下一步也是最关键的一步是为每个 PR 构建一个可运行的 Docker 环境。  
环境构建并非易事。目前常见的做法是让代理在代码沙箱中迭代构建环境，并配备相应的工具，使其能够反复尝试构建并根据构建结果进行自我纠正。  
理想情况下，这个过程应该完全自动化，但实际上，它尚未达到完美。对于某些语言或库版本，环境可能无法可靠地构建。在这种情况下，需要专家知识来优化代理的执行流程，这可以看作是将技能注入到代理中。  
完成后，我们就获得了每个 PR 的可运行虚拟 Docker 环境。

**公关标签和任务多样化**

接下来，我们对 PR 进行标签和路由。PR 包含多种数据类型——错误修复、功能添加、性能优化、测试构建或重构，以及其他数十种类别。  
路由是必要的，因为不同类型的 PR 需要不同的后续处理。

**错误修复示例**

对于标准的缺陷修复场景，我们提取 F2P（失败到通过）和 P2P（通过到通过）测试用例。如果一个黄金补丁通过了这些测试，则认为数据有效。然后，我们让模型作为代理在沙箱环境中修复缺陷，并使用 F2P 和 P2P 测试验证修复的正确性。P2P  
测试尤为重要，它可以确保在修复过程中不会引入新的缺陷。

**功能新增和性能优化**

对于新增功能，传统的 F2P/P2P 逻辑可能不再适用，因为测试通常依赖于新引入的代码（例如函数签名）。因此，我们专注于提取新增的测试点，并确保最终的黄金补丁能够通过这些测试。  
对于性能优化，则不存在 bug 修复流程。在这种情况下，我们会提取 P2P 测试，以验证优化前后性能是否存在稳定且显著的差异。  
不同类型的 PR 自然需要不同的处理策略。

**基于模型的验证**

即使是基本的 bug 修复场景，GitHub 上的原始 PR 也并非总是结构良好，测试用例也可能无法完全覆盖所描述的问题。这会导致仅凭问题描述无法修复 bug 的情况。  
为了解决这个问题，我们使用模型本身来验证测试用例和问题描述之间的一致性。如果缺少关键信息，模型会补充原始描述，使其成为一个独立且可解决的问题。

**任务转换与增强**

对于同一个 PR 或 issue，有很多方法可以重用数据：  
- 注入更多漏洞
- 合并相邻的提交或 PR 以增加难度（类似于 SWE-smith）
- 将 BugFix 任务转换为 SWE-Test 任务
在 SWE-Test 公式中，任务被反转：模型必须编写一个在应用补丁前失败、应用补丁后通过的测试用例，这要求模型具备强大的测试编写能力，同时还要保持可验证性和任务等效性。  
我们还可以构建代码审查任务，这些任务不一定需要可运行的环境。模型执行静态分析、审查代码变更并识别问题。可以使用另一个 LLM 来验证一致性，这使得此类任务具有近似可验证性，同时提供了更大的多样性。

**最终 SWE 数据集**

最终，我们获得了包含以下内容的 SWE 风格数据集：  
- 原始问题描述
- 基于测试用例的完全可验证奖励
- 可运行的 Docker 环境
这些数据集同时用于SFT和RL。对于SFT，我们应用多支架拒绝采样来提高泛化能力。对于RL，多支架训练至关重要，因为不同的支架会引入不同的上下文管理和执行逻辑。在单一支架（例如，一个简单的ReAct循环）上进行训练会严重限制泛化能力。SWE  
数据背后的核心思想是： **基于GitHub原始数据构建由代理驱动的自动化数据管道，以生成多样化、可验证的SWE风格数据集和环境。**

**规模化结果**

- **超过 14 万个可变任务**

在 Multi-SWE 和 SWE-bench 等基准测试中，M2.1 的性能显著优于 M2，尤其是在多语言环境下。其性能在不同的框架下均保持稳定，展现出强大的适应性。  

### 专家驱动的数据综合：应用开发

![](https://www.minimax.io/_next/image?url=https%3A%2F%2Ffile.cdn.minimax.io%2Fpublic%2F3639df54-0ae5-46d4-968e-bf028f3796e1.png&w=3840&q=75)

我们将编码分为两类：  
- **SWE：** 现有代码库中具有固定验证条件的任务
- **应用开发：** 从零开始的全栈应用开发
应用开发与软件工程的根本区别在于，应用开发无法完全预定义测试用例。因此，其奖励机制也截然不同。

**专家在环**

应用开发高度依赖于专家参与。前端、后端、Android 和 iOS 开发方面的内部专家会协助设计提示、元查询和基于评分标准的奖励机制，这些都无法完全自动化。  
专家还会通过系统提示注入最佳实践。在训练过程中，训练数据中可以省略系统提示，从而将专家启发式方法提炼为模型的默认行为。  
验证采用代理验证器模式：代理在沙箱环境中部署应用，通过 Playwright 等工具与其交互，并根据评分标准对应用性能进行评分。与 LLM 作为评判员不同，这需要多步骤的工具交互。M2.1  
**目前在 Hot Arena 排行榜的开源模型中排名第一** 。我们还构建了一个名为 VIBE Arena 的内部基准测试，稍后将详细介绍。

### 合成长时域任务生成：WebExplorer

![](https://www.minimax.io/_next/image?url=https%3A%2F%2Ffile.cdn.minimax.io%2Fpublic%2F21787880-2d3e-4db1-8d06-3498288fcdc0.png&w=3840&q=75)

除了编写智能体代码之外，我们也关注通用智能体场景，并将搜索作为其基础能力。  
我们的论文“Explore and Evolve for Training Long-Horizon Web Agents”（可在arXiv上获取）提出了一种两步法：  
- **探索：** 智能体自由探索网络，构建信息丰富的种子问题。
- **演化：** 查询通过迭代演化来增加复杂性。

**例子**

*从“巴西国家足球队* ”这样的种子开始 ，智能体发现了1950年世界杯、马拉卡纳惨案、裁判乔治·里德、他后来担任英格兰俱乐部主席的经历，以及1976年足总杯决赛——博比·斯托克的进球帮助球队获胜。  
在最后阶段，模型综合搜索过程中收集到的线索，生成一个信息丰富的初始查询。尽管这个查询包含大量信息，但仍然有清晰的检索入口。演化策略包括移除、混淆和替换。例如：  
- 将具体的比赛细节转化为模糊的描述，例如“ *采用独特赛制且没有淘汰赛阶段的世界杯* ”。
- *将“在足总杯中击败曼联* ”等关键信息替换 为“ *带领一支乙级联赛球队战胜一支顶级强队* ”，从而增加了检索难度。
- 删除容易搜索到的信息，例如球员去世时的年龄，这些信息很容易在维基百科上找到。
演化后的查询最终比原始问题复杂得多，并且缺乏明显的检索入口点，需要模型根据可用的线索逐步探索。

![](https://www.minimax.io/_next/image?url=https%3A%2F%2Ffile.cdn.minimax.io%2Fpublic%2F15b5e48a-92d6-4f4a-a1b4-0bd312166f12.png&w=3840&q=75)

此类长周期任务合成的评估标准是解决问题所需的平均推理轮数。原始问题平均需要约 7.9 轮推理，而改进后的版本则增加到 9.9 轮。此策略已应用于 M2.1 版本。  
**在 BrowsComp 排行榜上，M2.1 的性能接近 GPT-4.5 的 SOTA 指标，** 尤其是在启用上下文管理的情况下。上下文管理目前是搜索代理的主流方法：在评估过程中，上下文会不断清理，以保持简洁清晰，从而使模型能够有效地进行测试时扩展。

## 智能体强化学习框架和算法

### 锻造

![](https://www.minimax.io/_next/image?url=https%3A%2F%2Ffile.cdn.minimax.io%2Fpublic%2F67fe3d7c-75bb-407b-85cc-8278ee7aa4b1.png&w=3840&q=75)

我们使用内部开发的框架 Forge，它从 M2 开发之初就专为以智能体为中心的场景而设计。Forge 的一个关键特性是支持在任意智能体框架上运行强化学习。  
与 Forge 集成仅需实现四个接口：  
- **agent\_reprocess：** 预处理（初始化）
- **agent\_run：** 执行
- **agent\_postprocess：** 后处理
- **计算奖励：** 奖励计算
例如，即使是仅以二进制可执行文件形式提供的黑盒代理也可以集成。代理执行期间，其基本 URL 会被重定向到 Forge 的内部推理引擎服务。该引擎目前同时支持内部推理框架和 SGLang。重定向后，代理执行循环期间生成的所有日志都会持久化到推理服务器上。  
然后，数据协调器会对这些日志进行后处理，以提取子代理的轨迹。为了进一步提高训练效率，该框架会对轨迹执行智能前缀合并。  

### CISPO

![](https://www.minimax.io/_next/image?url=https%3A%2F%2Ffile.cdn.minimax.io%2Fpublic%2Fd0f5c852-1564-4916-a310-0c68b9cdc94d.png&w=3840&q=75)

从算法角度来看，在 M2.1 阶段之前，核心强化学习 (RL) 算法主要依赖于 CISPO，该算法最初在 MiniMax M1 论文中提出。M1 强调了两个关键方面：首先是 CISPO 本身固有的重要性采样截断设计；其次是针对当时发现的 FP32 精度问题的改进。  
  
第一部分涉及 CISPO 的目标函数。从概念上讲，它可以被理解为与 REINFORCE 目标函数非常相似。本质上，它是一个 REINFORCE 式的目标函数，并针对离策略设置进行了重要性采样修正。CISPO 引入的关键改进在于对重要性采样权重（即标量权重因子）应用了裁剪。在实践中，这种裁剪通常会设定一个上限，以确保梯度不会过大。从根本上讲，这种机制用于控制梯度更新的幅度。  
  
CISPO 最初设计于许多团队都在复现 R1-ZERO 流水线（包括字节跳动的 DAPO）的时期。在我们的复现过程中，我们发现了一个关键现象：在强化学习 (RL) 训练过程中，某些词元会被 PPO 的裁剪机制持续过滤掉。一旦被裁剪，这些词元实际上就永久失去了梯度。实证分析表明，这些词元通常是语篇词或过渡词，例如“wait”。这意味着 PPO 式的裁剪机制会阻止大量词元在训练过程中出现。  
  
在这种情况下，DAPO 的方法是提高 PPO 裁剪的上限。相比之下，CISPO 的方法旨在允许所有词元获得梯度，同时控制重要性采样权重系数。虽然这会引入一些偏差，但它显著降低了优化过程的整体方差。  
  
当我们在较小的模型上完成早期实验并将 RL 训练迁移到更大的 MiniMax M1 模型时，我们观察到整体奖励几乎没有增加。在记录并比较训练时间和推理时间的概率后，我们发现了清晰的分段水平线段，且它们之间的相关性远低于密集模型中的相关性。推理团队进一步逐层调试后发现，预测层（即LLM\_head层）的数值精度至关重要。将该层的精度恢复到FP32后，训练-推理一致性显著提高，从而实现了稳定且持续的训练效果。  
  
进入M2代后，主要变化是过渡到涉及多轮工具使用的智能体强化学习环境。这些工具调用本身会引入来自外部环境的噪声，使得执行轨迹更加极端、更偏离策略或更容易出现异常统计结果。  
  
在这些条件下，我们整合了多个领域提出的主流技术，包括多重重要性采样（MIS）和基于PPO的轨迹过滤。其核心思想是滤除统计特征异常、位于长尾分布中的轨迹，从而防止梯度过度波动，确保强化学习训练的整体稳定性。

![](https://www.minimax.io/_next/image?url=https%3A%2F%2Ffile.cdn.minimax.io%2Fpublic%2Fb2f640d5-cbc6-4863-9c08-d872aa4bad7c.png&w=3840&q=75)

此图改编自 Meta 的论文《扩展强化学习计算以用于 LLM 的艺术》。在该论文中，作者进行了一系列相当系统的实验对比，其结论与我们的结论基本一致。  
实验表明，CISPO 算法在整个扩展过程中表现卓越，无论是在收敛速度还是最终收敛上限方面。图的左侧部分展示了 CISPO 重要性采样技巧的效果，而右侧部分则突出了修复 FP32 精度问题所带来的收益。  
总而言之，该论文中的实验评估非常全面。对于对强化学习 (RL) 感兴趣的人，我强烈建议阅读该论文。

## 代理人评估

接下来，我想介绍一下我们与 M2.1 一起发布的三个基准测试：  
- **VIBE：** 应用程序开发执行的视觉和交互式基准测试
- **SWE评论**
- **OctoCodingBench**
目前，VIBE数据集已在Hugging Face上开源。但是，其基础设施尚未完全就绪，我们正在积极完善它。  

### 氛围

我们先来看 VIBE，它主要针对 AppDev（应用程序开发）场景。由于目前缺乏能够有效衡量该领域性能的排行榜，我们自行构建了这个基准测试。它涵盖了广泛的场景，包括前端开发、模拟 Android 和 iOS 以及后端任务。与 M2 相比，M2.1 在此基准测试中表现出显著的提升。

![](https://www.minimax.io/_next/image?url=https%3A%2F%2Ffile.cdn.minimax.io%2Fpublic%2F2b9c93b2-2c75-43fa-9e18-ed0b1fa8fd65.png&w=3840&q=75)

为了进行验证，我们采用了一种“代理即验证器”的方法，其中代理直接在真实环境中执行任务。奖励信号由三个维度组成：  
- **执行级别：** 验证代码是否编译并成功运行
- **交互层面：** 通过与工具和用户界面交互来评估业务逻辑是否正确
- **视觉水平：** 基于审美标准进行评分。虽然这一维度本身具有主观性，但我们侧重于评分者间一致性高的标准。

![](https://www.minimax.io/_next/image?url=https%3A%2F%2Ffile.cdn.minimax.io%2Fpublic%2Fec7ee0c6-a041-48c7-8aa7-b8480a34775f.png&w=3840&q=75)

与仅依赖静态屏幕截图进行评估的传统 LLM 作为评判者的方法相比，基于代理的验证能够实现动态交互，从而提供更全面的错误和实现缺陷视图。  

### SWE-Revier 和 OctoBench

![](https://www.minimax.io/_next/image?url=https%3A%2F%2Ffile.cdn.minimax.io%2Fpublic%2F9f2bbc9c-1e45-430d-9380-293b70d0af0c.png&w=3840&q=75)

另外两个基准测试是 **SWE-Review** 和 **OctoBench。SWE**  
**\-Review** 针对开发流程中的代码审查场景。它被设计成一个基准测试套件，涵盖多种编程语言和各种用例，其指标综合考虑了代码回忆率和错误率。OctoBench  
**评估** 智能体在智能体环境下的指令执行能力。与传统的指令执行 (IF) 排行榜（其中指令通常仅来自用户或系统提示）不同，基于智能体的场景中的指令还可以来自系统提醒、Claude.md 文件或工具模式。OctoBench **由** 内部开发，采用基于清单和评分标准的评分方式进行评估。
